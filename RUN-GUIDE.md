# Cloud-Native Intelligent Microservices Management Platform
## Complete Setup & Run Guide

This document explains what the project is, what you need to install before touching it, exactly how to run the whole thing step by step, and what to do when something goes wrong. It assumes no prior knowledge of the codebase.

---

## Part 1 — What This Project Actually Is

### The one-sentence version
An AI-powered cloud monitoring platform — like a self-built, smaller version of **Datadog, New Relic, or Dynatrace** — that watches your microservices and Kubernetes cluster, predicts problems before they happen, explains outages in plain English using AI, and sends alerts to Slack/email when something breaks.

### Who this helps and how
- **Engineering teams running microservices** get one dashboard showing every service's health, instead of checking 12 different logs by hand.
- **On-call engineers** get paged automatically (Slack/email/webhook) when something breaks, with an escalation if nobody acknowledges it in time.
- **SREs/DevOps** get a failure-risk score for each service *before* it goes down (not just an alert after it already failed), plus a plain-English root-cause summary generated by AI instead of having to read raw error logs at 3am.
- **Capacity planners** get a traffic forecast with a recommended number of server replicas, instead of guessing how much to scale up before a big event.
- **Anyone learning cloud/DevOps engineering** gets a real, working example of how 12 independent services, a shared library, an API gateway, a message queue, three databases of different kinds, machine learning, and a frontend all fit together in one coherent system — built the way an actual company would build it, not a toy tutorial.

### What it actually does, concretely
1. **Tracks every microservice's health** — is it up, degraded, or down (heartbeat-based, like a health monitor).
2. **Collects and graphs metrics** — CPU, memory, request counts, latency — over time.
3. **Watches your real Kubernetes cluster** — pods, nodes, deployments — and can scale a deployment up/down.
4. **Predicts future traffic** using a trained machine-learning model, with a recommended number of server replicas.
5. **Predicts failures before they happen** using a second machine-learning model that looks at resource trends (rising CPU, memory, restart counts).
6. **Explains problems in plain English** using Claude (Anthropic's AI) — reads your error logs and tells you the likely root cause and a suggested fix.
7. **Sends real notifications** — Slack, email, or a generic webhook — when something needs attention, and nags again if nobody acknowledges it.
8. **Stores files** — exported reports, log archives — in cloud-style object storage (S3-compatible).
9. **Shows all of this in a web dashboard** — dark-themed, real-time-updating, with charts and tables.

### The technology used, and why (short version)
| Layer | Technology | Why this one |
|---|---|---|
| Backend services | Python + FastAPI | Fast, modern, auto-generates API documentation |
| Database | PostgreSQL (+ TimescaleDB for metrics) | Industry-standard, reliable, good for both regular data and time-series data |
| Message queue | Apache Kafka | Handles high-volume data (like metrics/logs) without slowing down the services sending it |
| Cache / rate limiting | Redis | Extremely fast in-memory storage |
| Machine learning | LightGBM (traffic) + XGBoost (failure prediction) | Industry-standard models for this kind of tabular/time-series data |
| AI log analysis | Claude API (Anthropic) | Generates human-readable explanations from raw logs |
| Search/logs | OpenSearch | Full-text search over large volumes of log data |
| Object storage | MinIO (S3-compatible) | Same API as Amazon S3, runs locally for free |
| Frontend | React + TypeScript + Tailwind CSS | Modern, type-safe, fast to build with |
| Containers | Docker | Every service runs the same way on any machine |
| Orchestration | Kubernetes (manifests provided) | Industry-standard way to run containers at scale in production |
| Infrastructure-as-code | Terraform | Defines the cloud infrastructure (AWS) as code instead of clicking around a console |
| CI/CD | GitHub Actions | Automatically tests and deploys the code |

### How the pieces fit together
There are **12 independent backend services** (each one is its own small program with its own database), one **API Gateway** that all outside traffic goes through first (like a receptionist), and one **frontend website** that people actually look at. They all talk to each other over the network, the same way real company systems do. A full map of exactly which service does what is in `docs/01-SYSTEM-ARCHITECTURE.md` inside the project.

## Part 2 — What You Need To Install First

You have **two ways to run this**, and they need different things installed. Pick one.

### Option A — "Just run everything" (recommended for most people)
This uses Docker to run all 12 services + databases + everything at once, without installing Python, Node, Postgres, etc. individually.

**You need to install:**
1. **Docker Desktop** — this is the only real requirement.
   - Windows/Mac: download from https://www.docker.com/products/docker-desktop and install like any other app.
   - Linux: install `docker` and the `docker compose` plugin via your package manager (e.g. `sudo apt install docker.io docker-compose-plugin` on Ubuntu/Debian).
   - After installing, **open Docker Desktop and make sure it's running** (you'll see a whale icon in your system tray/menu bar). Everything below fails immediately if Docker isn't running.
2. **Git** (to download the project files) — https://git-scm.com/downloads, or skip this if you already have the project as a zip file.
3. A terminal / command line app — Terminal (Mac/Linux) or PowerShell/Command Prompt (Windows).

That's it for Option A. You do **not** need Python, Node.js, or any database installed on your computer — Docker handles all of that inside containers.

### Option B — "Run it directly on my machine" (for developers who want to edit code and see changes instantly)
This runs each service as a normal program on your computer, without Docker for the application code (Docker is still used for the databases/infrastructure, since installing Postgres/Kafka/Redis by hand is painful).

**You need to install, in addition to Docker Desktop above:**
1. **Python 3.12 or newer** — https://www.python.org/downloads/. On Windows, check the box "Add Python to PATH" during install.
2. **Node.js version 22 or newer** (only needed if you want to work on the frontend) — https://nodejs.org/ (download the "LTS" version).
3. **pip** (comes with Python automatically).

You do not need to separately install Postgres, Redis, Kafka, OpenSearch, or MinIO for Option B either — those still run via Docker in the background; only the actual application code (the 12 services + frontend) runs directly on your machine.

### Optional — only if you want to deploy to a real cloud (AWS)
Not needed to just run and try the project. Only needed if you want to actually deploy it to Amazon Web Services for real:
- **Terraform** — https://developer.hashicorp.com/terraform/downloads
- **AWS CLI**, configured with a real AWS account — https://aws.amazon.com/cli/
- **kubectl** — https://kubernetes.io/docs/tasks/tools/

### Optional — only if you want real AI-generated explanations
The platform's AI log-analysis feature works out of the box using a rule-based fallback (it still tells you something useful). If you want the *actual* Claude-generated explanations instead of the fallback:
- Get an API key from https://console.anthropic.com/ (requires creating an account; the API is pay-as-you-go, separate from a Claude.ai subscription).
- You'll paste this key into one config file — covered in Part 3.

## Part 3 — Running It, Step By Step (Option A: Docker, recommended)

### Step 1 — Get the project files
If you have the zip file, unzip it anywhere (e.g. your Desktop or Documents folder). If you're using Git:
```bash
git clone <repository-url>
cd cloud-native-platform
```
From here on, every command assumes your terminal is **inside the `cloud-native-platform` folder**. If a command fails with "file not found," the first thing to check is whether you're in the right folder (`pwd` on Mac/Linux, `cd` alone on Windows shows your current folder).

### Step 2 — Start Docker Desktop
Open the Docker Desktop application and wait until it says it's running. On Windows/Mac this is a regular app icon; on Linux, run:
```bash
sudo systemctl start docker
```

### Step 3 — Start the shared infrastructure (databases, cache, message queue, search, storage)
```bash
make infra-up
```
This starts Postgres, Redis, Kafka, OpenSearch, and MinIO in the background. The first time you run this, Docker will download several images — **this can take 5–15 minutes depending on your internet connection.** Subsequent runs are much faster (seconds).

If you don't have `make` installed (Windows users especially — `make` isn't built in), run the underlying command directly instead:
```bash
docker compose -f infra/docker-compose.yml up -d
```

**How to know it worked:** run `docker compose -f infra/docker-compose.yml ps` — you should see 6 containers all listed as `running` or `healthy` (postgres, redis, kafka, kafka-ui, opensearch, minio).

### Step 4 — Generate the security keys
Every service authenticates using a cryptographic key pair, generated once:
```bash
cd services/auth-service
python3 scripts/generate_keys.py
cd ../..
```
This creates a `keys/` folder inside `services/auth-service/` containing `private_key.pem` and `public_key.pem`. **Do not delete this folder** — every other service needs the public key to verify logins.

*(If `python3` isn't recognized, see the Troubleshooting section — this specific script needs Python installed even in the Docker-based Option A, since it's a one-time setup step, not something that runs continuously.)*

### Step 5 — Build and start every service
This is the big one — it builds all 12 backend services, the API gateway, and the frontend, then starts them all:
```bash
docker compose \
  -f infra/docker-compose.yml \
  -f services/auth-service/docker-compose.yml \
  -f services/monitoring-service/docker-compose.yml \
  -f services/metrics-service/docker-compose.yml \
  -f services/k8s-management-service/docker-compose.yml \
  -f services/dashboard-service/docker-compose.yml \
  -f services/traffic-prediction-service/docker-compose.yml \
  -f services/predictive-maintenance-service/docker-compose.yml \
  -f services/genai-log-analysis-service/docker-compose.yml \
  -f services/notification-service/docker-compose.yml \
  -f services/cloud-storage-service/docker-compose.yml \
  -f services/api-gateway/docker-compose.yml \
  -f frontend/docker-compose.yml \
  up -d --build
```
**This will take a while the first time** (10–20 minutes is normal — it's compiling/installing dependencies for 13 separate programs). Get a coffee. Every run after this one is much faster because Docker caches the parts that haven't changed.

**How to know it worked:** run
```bash
docker compose -f infra/docker-compose.yml -f services/auth-service/docker-compose.yml -f services/api-gateway/docker-compose.yml ps
```
(or just `docker ps` to see everything) — every container should show as `Up` and ideally `(healthy)`.

### Step 6 — Set up user accounts and permissions
The platform needs default roles (viewer/operator/admin) before anyone can log in usefully:
```bash
docker exec -it $(docker ps -qf "name=auth-service") python scripts/seed_rbac.py
```
If that exact command doesn't find the container, run `docker ps` first, find the container name that contains "auth-service", and substitute it:
```bash
docker exec -it platform-auth-service python scripts/seed_rbac.py
```

### Step 7 — Create your first account
Open a browser and go to **http://localhost:3000** — you should see the login page. Since you don't have an account yet, you need to create one via the API directly (there's no public "sign up" button by design — this is an internal ops tool, not a consumer app):

```bash
curl -X POST http://localhost:8000/api/v1/auth/register \
  -H "Content-Type: application/json" \
  -d '{"email":"you@example.com","password":"YourPassword123"}'
```
(Password must contain at least one number and one uppercase letter, minimum 8 characters.)

By default, new accounts get the "viewer" role (read-only). To give yourself full admin access, run:
```bash
docker exec -it $(docker ps -qf "name=auth-service") python3 -c "
import asyncio
from app.core.config import AuthServiceSettings
from platform_common.db import Database
from sqlalchemy import text

async def main():
    settings = AuthServiceSettings()
    db = Database(settings.DATABASE_URL)
    async with db.session_scope() as session:
        await session.execute(text('''
            INSERT INTO user_roles (user_id, role_id)
            SELECT u.id, r.id FROM users u, roles r
            WHERE u.email='you@example.com' AND r.name='admin'
            ON CONFLICT DO NOTHING
        '''))
asyncio.run(main())
"
```
(Replace `you@example.com` with the email you registered.) This is a manual step because the platform doesn't yet have an admin-management screen — a known, documented limitation, not an oversight.

### Step 8 — Log in and look around
Go back to **http://localhost:3000**, log in with the email/password from Step 7, and you should see the Executive Dashboard. Since this is a fresh install with no data yet, most numbers will show as zero or empty — that's expected. See Part 4 for how to put some data in so the dashboards actually show something.

### Step 9 — Shutting everything down
When you're done:
```bash
docker compose -f infra/docker-compose.yml -f services/auth-service/docker-compose.yml -f services/monitoring-service/docker-compose.yml -f services/metrics-service/docker-compose.yml -f services/k8s-management-service/docker-compose.yml -f services/dashboard-service/docker-compose.yml -f services/traffic-prediction-service/docker-compose.yml -f services/predictive-maintenance-service/docker-compose.yml -f services/genai-log-analysis-service/docker-compose.yml -f services/notification-service/docker-compose.yml -f services/cloud-storage-service/docker-compose.yml -f services/api-gateway/docker-compose.yml -f frontend/docker-compose.yml down
```
This stops everything but keeps your data (database contents) intact for next time. To also wipe all data and start completely fresh, add `-v` to the end of that command.

## Part 4 — Putting Some Real Data In (so the dashboards aren't empty)

A brand-new install has no services registered and no metrics. To see the platform actually do something:

1. **Register a service** (so it shows up in the dashboards):
```bash
TOKEN=$(curl -s -X POST http://localhost:8000/api/v1/auth/login -H "Content-Type: application/json" -d '{"email":"you@example.com","password":"YourPassword123"}' | python3 -c "import sys,json;print(json.load(sys.stdin)['access_token'])")

curl -X POST http://localhost:8000/api/v1/services \
  -H "Content-Type: application/json" -H "Authorization: Bearer $TOKEN" \
  -d '{"name":"checkout-api","type":"microservice","owner_team":"payments"}'
```
2. **Send it a heartbeat** so it shows a status:
```bash
SERVICE_ID=<the "id" field from the response above>
curl -X POST http://localhost:8000/api/v1/services/$SERVICE_ID/heartbeat \
  -H "Content-Type: application/json" -H "Authorization: Bearer $TOKEN" \
  -d '{"healthy": true, "latency_ms": 42}'
```
3. Refresh the dashboard — you should now see "checkout-api" show up as healthy.

The Kubernetes dashboard will show sample data automatically (it runs in "demo mode" by default, showing realistic simulated pods/nodes, since connecting to a real Kubernetes cluster is optional — see Part 6).

## Part 5 — Running It Without Docker for the Application Code (Option B)

Only do this if you want to actively edit the code and see changes reload instantly. This still needs Docker for the databases (Step 1–3 above are identical), but each service runs as a normal Python program instead.

For **each** service (repeat the pattern below, changing the folder and port):
```bash
cd services/auth-service
pip install -r requirements-dev.txt
cp .env.example .env
# open .env in a text editor and fill in JWT_PRIVATE_KEY/JWT_PUBLIC_KEY from the keys/ folder (Step 4 above)
python -m alembic upgrade head
uvicorn app.main:app --reload --port 8001
```
Every service's exact port is listed in the table below. You'd need a separate terminal window/tab open for each service you want running (up to 12 + the gateway).

| Service | Port |
|---|---|
| API Gateway | 8000 |
| Auth Service | 8001 |
| Monitoring Service | 8002 |
| Metrics Service | 8003 |
| Kubernetes Management Service | 8004 |
| Dashboard Service | 8005 |
| Traffic Prediction Service | 8006 |
| Predictive Maintenance Service | 8007 |
| GenAI Log Analysis Service | 8008 |
| Notification Service | 8009 |
| Cloud Storage Service | 8010 |
| Frontend (dev server) | 5173 |

For the frontend specifically:
```bash
cd frontend
npm install
cp .env.example .env
npm run dev
```
Then visit **http://localhost:5173** instead of :3000 (Vite's dev server, with instant hot-reload on save).

**In practice, most people should use Option A (Docker) unless they specifically intend to edit backend code** — running 13 separate terminal windows by hand is tedious and easy to get wrong.

## Part 6 — Optional Features (safe to skip)

These are genuinely optional. The platform works correctly without them — it just uses a documented fallback instead.

### Real AI-generated log explanations (instead of the rule-based fallback)
1. Get an API key from https://console.anthropic.com/
2. Open `services/genai-log-analysis-service/.env`
3. Set `ANTHROPIC_API_KEY=sk-ant-...` (your real key)
4. Restart that one service: `docker compose -f services/genai-log-analysis-service/docker-compose.yml up -d --build`

Without this, the "explain this problem" feature still works — it just uses simpler pattern-matching instead of AI, and tells you so honestly in its response (`"source": "fallback"` instead of `"source": "llm"`).

### Real Slack/email notifications (instead of no delivery)
Open `services/notification-service/.env` and fill in any of:
```
SLACK_WEBHOOK_URL=https://hooks.slack.com/services/...
SMTP_HOST=smtp.yourprovider.com
SMTP_TO_ADDRESSES=["you@example.com"]
```
Any channel left blank is simply skipped — notifications still get recorded in the system, they just don't get delivered anywhere externally.

### Connecting to a real Kubernetes cluster (instead of demo/simulated data)
Open `services/k8s-management-service/.env`, change `CLUSTER_MODE=demo` to `CLUSTER_MODE=kubernetes`, and either run this service inside a real cluster, or mount a working kubeconfig file. Without this, the Kubernetes dashboard shows realistic simulated data instead of your real cluster — clearly useful for trying the platform out, not for real production monitoring.

## Part 7 — Troubleshooting (Problem → Cause → Fix)

### "docker: command not found" / "docker compose: command not found"
**Cause:** Docker Desktop isn't installed, or isn't on your system PATH.
**Fix:** Reinstall Docker Desktop from https://www.docker.com/products/docker-desktop and restart your terminal (and your computer, if it still doesn't work) after installing.

### "Cannot connect to the Docker daemon"
**Cause:** Docker Desktop is installed but not currently running.
**Fix:** Open the Docker Desktop application and wait for it to fully start (the whale icon stops animating) before running any `docker` command.

### A container keeps restarting / shows "unhealthy"
**Cause:** Usually means it's waiting on another container that isn't ready yet (e.g. a service starting before Postgres finishes initializing).
**Fix:** Wait 30–60 seconds and check again — most of these resolve themselves. If not, view its logs to see the actual error:
```bash
docker logs <container-name>
```
(find the exact name via `docker ps -a`).

### "Port already in use" / "port is already allocated"
**Cause:** Something else on your computer is already using that port (commonly 5432 for Postgres, or 8000-8010, or 3000/5173).
**Fix — Alternative 1:** Stop whatever else is using that port. On Mac/Linux, find it with `lsof -i :5432` (replace the port number) and stop that process.
**Fix — Alternative 2:** Change the port this project uses instead. Open the relevant `docker-compose.yml` file and change the left-hand side of the port mapping, e.g. `"5432:5432"` → `"5433:5432"`, then update the corresponding `.env` file to match.

### Login fails with "Invalid email or password" even though you're sure it's right
**Cause 1:** You haven't registered yet — Step 7 in Part 3 is required first.
**Cause 2:** Your account got locked after 5 failed attempts (a security feature — auto-unlocks after 15 minutes).
**Fix:** Wait 15 minutes, or register a fresh account with a different email to keep testing immediately.

### Every API call returns "403 Forbidden"
**Cause:** RBAC roles were never seeded (Step 6 in Part 3 was skipped), so your account has no permissions attached, or you're using the default "viewer" role which is read-only for write actions.
**Fix:** Re-run Step 6, then check your account's role — most write actions (registering a service, sending a heartbeat) need the "operator" or "admin" role, not "viewer". See Step 7's admin-promotion command as a template for granting any role.

### Frontend loads but shows "Couldn't load this data" everywhere
**Cause 1:** The API Gateway isn't running or isn't reachable.
**Fix:** Check `docker ps` — is `platform-api-gateway` listed as `Up`? If not, check its logs: `docker logs platform-api-gateway`.
**Cause 2:** The frontend is pointed at the wrong gateway address.
**Fix:** Check `frontend/.env` — `VITE_API_BASE_URL` should be `http://localhost:8000`. If you changed this, rebuild the frontend container.

### "relation does not exist" / database errors on startup
**Cause:** Database migrations haven't run yet for that service.
**Fix:** This should happen automatically via Docker, but if running Option B manually, make sure you ran `python -m alembic upgrade head` inside that service's folder before starting it.

### GenAI log analysis always says `"source": "fallback"` even with an API key set
**Cause:** Either the key is invalid/expired, or the service wasn't restarted after you added the key to `.env`.
**Fix:** Double-check the key is correct and has no extra spaces, then rebuild that one service: `docker compose -f services/genai-log-analysis-service/docker-compose.yml up -d --build`. This is a working fallback either way — not a broken feature.

### Kafka / OpenSearch take forever to start, or seem to hang
**Cause:** Both are genuinely heavier Java-based services and can take 1–2 minutes to become ready on a slower machine, especially the first time.
**Fix:** Just wait — check readiness with `docker compose -f infra/docker-compose.yml ps`. If it's still unhealthy after 5 minutes, check available memory — Docker Desktop needs at least 4GB RAM allocated to it (Docker Desktop → Settings → Resources) for the full stack to run comfortably.

### "No space left on device" from Docker
**Cause:** Docker images/containers/volumes have built up over time and filled your disk.
**Fix:** Run `docker system prune -a --volumes` to clean up everything Docker isn't actively using (this is safe but will require re-downloading images next time you start up).

### I don't have `make` installed (common on Windows)
**Cause:** `make` isn't included by default on Windows.
**Fix — Alternative:** Every `make` command in this guide has the underlying raw command shown right below it — just run that instead. You never strictly need `make`, it's only a shortcut.

### Nothing above fixed it
**Fix:** Run `docker compose -f infra/docker-compose.yml logs` (and the equivalent for whichever service is failing) and read the actual error message near the bottom — it almost always states plainly what's wrong (a missing environment variable, a connection refused, etc.). Searching that exact error message online is usually the fastest path from there.
